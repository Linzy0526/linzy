# 前端代码提交规范化

> 本文主要从代码风格统一和git提交格式统一两个方向去规范代码的提交

## 前言

在团队开发中，每个人的开发风格和习惯迥异，常常会出现以下问题：
- 代码格式不统一，不同团队成员存在不同的格式化配置，导致提交的代码格式不统一，阅读体验差
- 无效的git提交，代码格式不统一导致存在提交了一些与git说明无关的代码
- 变更历史不明，在提交代码时没有良好的提交习惯，对每次变更做出明确的标志和说明

怎么做？

推荐使用前端规范全家桶 `ESLint + Prettier + husky + lint-staged`

## ESLint 安装及使用

eslint 是一个代码检测工具，用于检测代码中潜在的问题和错误，作用提高代码质量和规范。

### 安装ESLint

1.安装eslint依赖

``` shell
npm install eslint -save-dev
```

2.快速构建eslint配置文件
``` shell
npm init @eslint/config
```
初始eslint配置并进入以下Vim窗口进行配置
``` shell
###  选择应用ESLint的意图，当前选择时为了检查语法、发现问题并强制执行代码样式

```

3.配置eslint规则
执行完上面的命令，在项目根目录根据上面配置会生成 `.eslintrc.js` 文件，可以在该文件`rules`属性内配置相应规则
```
// .eslintrc.js
module.exports = {
  env: {
    browser: true,
    es2021: true,
  },
  parser: "vue-eslint-parser",
  plugins: ["vue", "@typescript-eslint", "prettier"],
  extends: [
    "eslint:recommended",
    "plugin:vue/vue3-recommended",
    "plugin:@typescript-eslint/recommended",
    // 初始化未生成，需要在后续配置 prettier 再添加，解决冲突
    "plugin:prettier/recommended",
  ],
  parserOptions: {
    ecmaVersion: "latest",
    parser: "@typescript-eslint/parser",
    sourceType: "module",
  },
  rules: {
    "prettier/prettier": "error",
    "arrow-body-style": "off",
    "prefer-arrow-callback": "off",
    "@typescript-eslint/ban-ts-comment": "off",
    "@typescript-eslint/no-explicit-any": "warn",
    "vue/multi-word-component-names": "warn"
  },
};

```

上面的配置中本文中删除了 `overrides` 属性的配置，该属性的配置用于允许你为特定文件、目录或 glob 模式指定不同的 ESLint 配置，在初始化配置中主要是配置了 `.eslintrc.cjs` 的 ESLint，由于在项目中应用了 `.eslintignore` 文件去做了剔除，所以不再做额外配置

4..eslintignore文件配置
由于 ESLint 校验的是根目录下所有匹配到的文件，项目在运行打包的时候必然存在像 `node_modules` 和 `dist` 等不需要检验的文件

我们可以应用 `.eslintignore` 去去除不需要检验的文件或目录，编写方式与 `gitignored` 类似

5.vscode安装ESLint工具
在vscode扩展工具商城安装ESLint工具，安装成功后再setting.json中配置开启ESlint校验
``` json
// setting.json
{
"eslint.validate": [
    "javascript",
    "javascriptreact",
    "vue",
    "html",
    "typescript"
  ]
}
```
开启校验后，我们可以在vscode实时看到eslint的报错提示


## Prettier 安装及使用
Prettier 是一个代码格式化工具，旨在帮助开发者自动格式化代码，以确保代码风格的一致性和可读性。它支持多种编程语言，包括 JavaScript、TypeScript、HTML、CSS、JSON 等等。

1.安装Prettier
``` shell
npm install prettier -save-dev
```

2.配置Prettier风格
首先我们可以在vscode中配置风格完成全局的Prettier配置，除此之外也可以在项目的根目录的 `.prettierrc.cjs` 配置
``` js
// 项目pretter配置
module.exports = {
  // 一行最多 150 字符
  printWidth: 150,
  // 使用 2 个空格缩进
  tabWidth: 2,
  // 不使用 tab 缩进，而使用空格
  useTabs: false,
  // 行尾需要有分号
  semi: true,
  // 使用双引号
  singleQuote: false,
  // 对象的 key 仅在必要时用引号
  quoteProps: "as-needed",
  // jsx 不使用单引号，而使用双引号
  jsxSingleQuote: false,
  // 末尾使用逗号
  trailingComma: "all",
  // 大括号内的首尾需要空格 { foo: bar }
  bracketSpacing: true,
  // jsx 标签的反尖括号需要换行
  jsxBracketSameLine: false,
  // 箭头函数，只有一个参数的时候，也需要括号
  arrowParens: "always",
  // 每个文件格式化的范围是文件的全部内容
  rangeStart: 0,
  rangeEnd: Infinity,
  // 不需要写文件开头的 @prettier
  requirePragma: false,
  // 不需要自动在文件开头插入 @prettier
  insertPragma: false,
  // 使用默认的折行标准
  proseWrap: "preserve",
  // 根据显示样式决定 html 要不要折行
  // htmlWhitespaceSensitivity: "css",
  // 换行符使用 lf
  endOfLine: "auto",
  vueIndentScriptAndStyle: true,
  htmlWhitespaceSensitivity: "strict",
  overrides: [
    {
      files: "*.vue",
      options: {
        parser: "vue",
        vueIndentScriptAndStyle: true,
        htmlWhitespaceSensitivity: "ignore", // 标签属性单独放在新行上
      },
    },
  ],
};
```
3.解决 ESLint 和 Prettier 的冲突
``` shell
npm install eslint-config-prettier eslint-plugin-prettier -save-dev
```
- eslint-config-prettier ：关闭eslint中与prettier相互冲突的规则。
- eslint-plugin-prettier : 允许eslint用prettier格式化代码的能力。 安装依赖并修改.eslintrc文件
  
在.eslintrc文件中配置Prettier（上文已完成配置）

## Husky 安装及使用
Husky 是一个用于设置 Git 钩子的工具，可以在 Git 事件发生时运行自定义脚本。下面是一个使用 Husky 的简单方案，以在提交代码前运行 ESLint 和 Prettier 进行代码检查和格式化。

1.首先，确保你的项目中已经安装了 Husky 和 lint-staged，你可以使用以下命令进行安装：
``` shell
npm install husky lint-staged --save-dev
```

2.在项目的根目录中，打开 package.json 文件，并在其中添加一个 lint-staged 配置，以告诉 lint-staged 在提交前运行 ESLint 和 Prettier
``` json
"lint-staged": {
  "*.{js,ts,vue}": [
    "eslint --fix",   // 修复 ESLint 错误
    "prettier --write" // 格式化代码
  ]
},
```
这个配置表示 lint-staged 会在提交前检查和格式化所有 .js、.ts 和 .vue 文件

<span style="color:red">(建议)在开发中建议不是直接修复避免意想不到的bug，而是直接报错，终止commit</span>

``` json
"lint-staged": {
  "*.{js,ts,vue}": [
    "eslint",
  ]
},
```

3.现在，我们将配置 Husky 钩子以在提交前运行 lint-staged。在命令行中执行以下命令：
``` shell
npx husky install
npx husky add .husky/pre-commit
```

4.打开 .husky/pre-commit 文件，并确保它包含以下内容
``` bash
#!/bin/sh
. "$(dirname "$0")/_/husky.sh"

# 使用 lint-staged 运行代码检查和格式化
npx lint-staged
```

Husky的所有Git钩子:
- pre-commit： 在执行 git commit 命令之前触发。通常用于在提交前运行代码检查和格式化，以确保提交的代码质量。

- commit-msg： 在提交消息被创建后但提交前触发。可以用于自定义提交消息的验证，例如检查提交消息是否符合特定格式。

- pre-push： 在执行 git push 命令之前触发。通常用于在推送前运行测试或其他自定义检查。

- pre-rebase： 在执行 git rebase 命令之前触发。可以用于在变基前运行自定义操作，例如检查是否有未提交的更改。

- post-merge： 在执行 git merge 命令后触发。可以用于在合并后运行自定义操作。

- post-checkout： 在执行 git checkout 命令后触发。可以用于在检出分支后运行自定义操作。

- post-commit： 在执行 git commit 命令后触发。通常用于执行与提交相关的后续操作。

- post-rewrite： 在执行 git commit --amend、git rebase 等命令后触发。可以用于在重写历史后运行自定义操作。


# Commitizen 安装及使用
Commitizen 是一个用于规范化 Git 提交消息的工具，它帮助开发团队创建一致的提交消息格式，以便更容易跟踪和管理项目的提交历史。通常，它与 Conventional Commits 规范一起使用

##### 安装交互式窗口提交规范信息

1.安装交互式依赖 `commitizen` 及其适配器 `cz-conventional-changelog`
``` bash
npm install commitizen cz-conventional-changelog -save-dev
```

2.在项目的 package.json 文件中，添加一个 config.commitizen 部分来配置 Commitizen。指定 path 为你所选择的适配器的路径，通常是 cz-conventional-changelog

``` json
"config": {
  "commitizen": {
    "path": "cz-conventional-changelog"
  }
}
```

3.在 package.json 中的 scripts 字段中添加一个 commit 的命令。

``` json
"scripts": {
  "commit": "git-cz"
}
```
后续可以直接用 `npm run commit` 代替  `git commit` 命令，此时我们可以通过Vim窗口提交规范的 commit message

##### 安装交互式窗口提交规范信息
虽然我们可以通过交互式窗口创建统一的规范提交信息，但是限制不了直接通过  `git commit` 命令去提交超限制的内容，因此可以通过 `commitlint`  结合 `Husky` 钩子去限制提交内容

1.安装依赖
``` bash
npm install commitlint @commitlint/config-conventional -save-dev
```

2.添加 Husky commit-msg钩子
``` bash
npx husky add .husky/commit-msg "npx --no-install commitlint --edit "$1""
```

3.设置规则
在根目录创建 `commitlint.config.js` 文件并导入通用规则
``` js
// commitlint.config.js
module.exports = {extends: ['@commitlint/config-conventional']};
```
